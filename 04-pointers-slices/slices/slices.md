## スライスはデータを持たない

- スライスは配列の一部
- スライスはデータを持たない、データは元の配列
- スライスはビュー、窓。

## スライスを変更すると配列も変更される

## スライスとは

```
a := []int{1, 2, 3, 4, 5}  // スライスリテラル（型は []int）
```

- メリット
    - コピーが発生しない
    - 関数で配列を変更できること
    - メモリ効率が良いこと

## スライスリテラル
 
- 配列リテラルは長さ指定する
- 内部で配列を作る -> その配列全体を指すスライスを返す
    - `[]int{1, 2, 3}`
    - 名前のない配列で長さ３の配列を作る
    - その配列全体を指すスライスを渡す

## 空のスライスとnilスライス

- nilスライスを使う方が多い
    - jsonエンコード時にnullを返す
    - == nilでtrue
- []int{}
    - == nilでfalse

## スライスの長さ、容量

- len(s)で取得
- スライスに含まれる要素数
- cap(s)
- スライスが拡張できる最大サイズ
    - スライスの最初の要素から見て、裏配列の末尾までなん要素分使えるか？

## 再スライスで長さを変える

- 容量を超えて伸ばすことはできない
- lenはスライスとして見えている(裏の配列の)要素の個数
- capは今の見える範囲の先頭から裏にある配列の末尾まで使える上限

## 容量がなぜ必要なのか

- appendしたいから。

## nilスライス

- スライスを宣言だけして初期化しない
```
var s []int
var s [2]int // 配列
```

- s == nil // true
- len(s) == 0
- cap(s) == 0
- 元の配列がない
- 推奨はnilスライスがよい
    - 空の状態を表現できる

## 空のスライス

```
s := []int{}
```

- これはnilではない

## make関数

- 容量を事前に確保したい時に使える
- サイズが実行時に決まる場合。
- 大量の要素を使う場合
    - 容量を事前に確保することでappendが効率的に。
        - append のたびに「新しい裏配列へ引っ越し＋全要素コピー」が起きてしまうのでそれを防ぐ。
        - cap不足になると新配列へコピーが走る。
- パフォーマンスを最適化したい時

## 二次元配列

- スライスのスライスで表現する
- リテラルで作る
    - 初期値がある時
- makeで作る
    - サイズが実行時に決まる時
- appendで追加していく

## append

- スライスに要素を足した新しいスライスを返すbuilt-in関数
    - 新しいスライスかと言って、同じ裏配列で、スライスヘッダ(ポインタ、len, cap)が新しくできる。
    - スライスっつーのは実体はスライスヘッダをコピーしているだけ。
    - appendで更新されたヘッダを返す。
        - backの中身に新しい値が入る。lenが増える。
- 容量が足りている場合
    - 元の配列を使うので、高速
- 容量が足りない場合
    - 新しい配列を確保
    - 元の要素をコピー
    - 新しい要素を追加
- append は必ず戻り値を代入する（`s = append(s, x)`）
- cap 内: 同じ back、ヘッダの len 更新
- cap 超え: 新しい back + コピー + 追加（再割り当て）
- スライスの結合
    - append(s1, s2, s3)
